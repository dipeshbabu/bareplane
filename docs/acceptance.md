# v0.1 acceptance baseline

Bareplane's v0.1 path is Proxmox infrastructure → owned Linux/kubeadm/Cilium bootstrap → private Kubernetes access and health → minimal Argo → verified user-owned GitOps handoff. AI, data services, and persistent-storage expansion are outside this baseline.

## What automated CI proves

`TestAcceptanceMockedLifecycle` exercises one project through `init`, strict validation, authenticated fake-Proxmox doctor/discovery, infrastructure render, real saved-plan/attestation control flow, bootstrap render/doctor/TCP-banner checks/explicit trust/authenticated fact parsing, bootstrap phase orchestration, GitOps rendering, installation/handoff control flow, and status transitions. Only provider responses and external command effects are synthetic. Fake keys, plans, and kubeconfig data are deliberately not usable on a real host or cluster.

The test injects failures at Terraform plan/apply, node join, Argo install, and handoff; failed phases cannot advance state or leave a replayable Terraform attestation. It repeats the stage-aware workflow and checks no-op infrastructure state, health-only bootstrap, trust reuse, installer non-reclamation, handoff verification, secret exclusion, and private artifact permissions. Refusing repeated `init`, strict fresh-host preflight on an already initialized host, or installation after handoff is an intentional safety boundary, not permission to overwrite state.

Independent disposable-VM jobs exercise real Debian/Ubuntu preparation, a three-control-plane/one-worker kubeadm topology, Kubernetes/Cilium/etcd/DNS/service health, explicit reset and data preservation, actual Argo installation, and real pinned-then-following GitOps handoff. They compare stable resource identities on reruns. They never use an operator's Proxmox API or machines. Terraform syntax and saved-plan command-shape smoke tests use the actual pinned Terraform CLI.

The final `v0.1 acceptance` job requires every quality and VM dependency to succeed. Skipped, cancelled, missing, and failed dependencies are not acceptance. **Hosted CI is not evidence that a specific physical Proxmox environment passed.** The operator procedure below supplies that separate release-candidate evidence.

## Reference topology and compatibility

Use [examples/acceptance.yaml](../examples/acceptance.yaml) as a documentation-only reference: three control-plane VMs and one worker, each 4 vCPU/8 GiB/64 GiB, Ubuntu 24.04 amd64, a common on-link IPv4 management network, and an unused API VIP. The documentation addresses and `.invalid` endpoint must be replaced. Guest names/addresses and VIP must match the actual approved lab network. DHCP reservations/static-address provisioning must be arranged explicitly; Bareplane does not infer addresses from arbitrary Terraform outputs.

The [machine-readable compatibility record](compatibility.json) captures the current reference pins. Proxmox VE 9.2 is the reference target; [bpg/proxmox 0.111.1 upstream compatibility](https://github.com/bpg/terraform-provider-proxmox/tree/v0.111.1#readme) targets 9.x, limits 8.x support, and excludes 7.x. Record the exact Proxmox patch release and resolved provider lock version in RC evidence. The renderer's `~> 0.111.1` constraint is not a substitute for the exact checked dependency lock.

Use the existing supported Linux/WSL controller toolchain and standard CA trust. Native Windows is not an execution controller. The real VM CI image is checksum-pinned in its harness; record the actual imported cloud image checksum in Proxmox evidence as well. No GPU, Ceph, SSO, public ingress, automated DNS, or private Git credentials are required for this baseline.

## Operator-run Proxmox release-candidate procedure

This procedure is **not run automatically**. Use a disposable, explicitly authorized Proxmox lab, sufficient free resources, and a dedicated project/Git repository. Review the scoped Proxmox token permissions and TLS trust; keep credentials only in the documented environment variables. Do not use production VMs, unrelated disks, or another project's state. Have out-of-band console access and an agreed recovery plan.

1. Select an immutable source commit from the default branch. Run the `Candidate CI prerequisite` workflow for that SHA, or run its read-only verifier with authorized GitHub read access. It must verify the latest successful CI run and every required job for that exact source. It performs no publishing and still reports that real Proxmox evidence is required.
2. Build/use that source revision and capture `bareplane version`, tool versions, Proxmox version, provider lock/checksum, guest image checksum, lab identifier, and operator/date. Never publish tokens, private keys, kubeconfig contents, join credentials, Terraform state, or private phase logs.
3. Create a fresh project with `bareplane init`, adapt the reference configuration to the approved lab, and generate a dedicated controller key. Set up exact VM address reservations and an unused on-link VIP. Run `validate` and `doctor`; every required prerequisite must pass.
4. Run `bareplane plan` and verify only the intended missing owned machines are proposed. Run `bareplane render` and inspect generated Terraform. Run `bareplane terraform plan`, review the actual saved plan, then explicitly run `bareplane terraform apply --approve bp-rc`. Refuse unexpected existing guests or unmanaged collisions; do not force adoption.
5. Confirm only the expected VMs and Bareplane ownership tags were created. Run `bootstrap render`, `bootstrap doctor`, and `bootstrap check`. Review SSH fingerprints against the out-of-band VM consoles, then run `bootstrap trust` interactively. Do not pipe automatic approval into host trust. Run authenticated `bootstrap preflight` on these fresh machines.
6. Run `bootstrap apply --approve bp-rc`. Require all eight phases and the real health gate, a private project-scoped kubeconfig, exact node/role/version topology, healthy etcd, bootstrap-owned Cilium with no kube-proxy, working CoreDNS, and successful temporary network probes with cleanup.
7. Run `gitops render`, review the exact public export, copy it to a separate user-controlled checkout, and publish it at the configured revision/root. Keep all `.bareplane` execution state and credentials out of Git. Run `gitops install --approve bp-rc`, then `gitops handoff --approve bp-rc`. Require actual root/child `Synced`/`Healthy` status, Argo self-management, and no Cilium tracking by Argo.
8. Run `bareplane status` and record the three applicable lifecycle fields. Status reads local success records; also capture sanitized live readiness summaries, not just the status booleans.
9. Repeat validation, discovery, rendering, and a fresh Terraform plan. Require no destructive/unexpected drift. Do not replay an old saved plan. Repeat bootstrap apply (health only), trust (unchanged), GitOps render, and handoff (read-only root verification). Verify VM identities, root UID/generation, and original Argo resource UIDs remain stable. The installer must refuse to reclaim handed-off state.
10. Exercise a controlled failure/recovery case in a **separate disposable project** before handoff, using the documented bootstrap recovery limits. Confirm no false phase advancement and preserve an unrelated test data disk/sentinel. Bootstrap reset must refuse a cluster already carrying Argo/platform state. Do not turn acceptance into an implicit production teardown.

Record evidence against the exact source SHA using the [release checklist](release-checklist.md). If a required check fails, fix it in a focused PR and rerun all CI and affected operator acceptance for the new source. A green CI prerequisite alone does not certify a physical lab or authorize release publication.
